# Puzzle Cam

用 Electron 读取摄像头画面并实时预览的桌面小程序，带一路 OpenCV 视觉分析（Python 侧车）。

Windows / Linux / 树莓派（Pi 4、Pi 5，64 位系统）通用：摄像头一律走 `<video>` + `getUserMedia`，
在三个平台上是同一条代码路径；Python 侧车只做纯函数式的图像处理，不碰相机。

## 运行

```bash
npm install                                          # 首次安装，会下载 Electron 运行时
python -m pip install -r vision/requirements.txt     # OpenCV 侧车依赖（不装也能用，只是没有 OpenCV 分析）
npm start
```

自检（不用手点，自动开一次摄像头并校验落盘链路 + 视觉链路）：

```bash
npm run smoke
```

## 功能

| 功能 | 说明 |
| --- | --- |
| 实时预览 | 点击「开启摄像头」授权后 `<video>` 直接播放 `getUserMedia` 数据流 |
| 设备切换 | 下拉框列出所有摄像头，切换即重建数据流 |
| 分辨率 | 默认 / 480p / 720p / 1080p / 2K / 4K，按 `ideal` 约束请求，设备不支持时自动降级 |
| 画面方向 | 摄像头倒着装的（转了 180°），抽帧时统一转回来（见下文 `CAMERA_ROTATE_180`） |
| 拍照保存 | 把当前帧画到 canvas，弹系统保存对话框，输出 PNG |
| 识别一次 | 点按钮抓**一帧**交给 Python 侧车，算完就把结果定住，**不持续跑**；再点一次重来 |
| 主画面 | 显示**裁切矫正后的绿板**（摆正的板面），不是原始摄像头画面 |
| 左右分区 | 板子中间那条线当分界线：左「拼图区」显示**拼好的矩形**，右「识别区」显示**识别到的碎片** |
| 叠加层 | 碎片轮廓 + 编号 + 板上的线条，画在矫正后的板面上 |
| 浮动小窗 | 左下是拼好的矩形，右下是原始摄像头画面（对位置和光照用） |
| 设置页 | 点顶栏「设置」整页打开：**配置项 + 调试功能都在里面**（分析分辨率、坐标映射、串口连接、命令测试、两块日志） |
| 舵机 / 电磁铁 | 工具栏上的常驻开关，**不用展开控制台**就能按；开着时按钮变绿，没连机器时是灰的 |
| 吸 / 放 | 把「舵机放下 → 电磁铁吸合/释放 → 舵机升起」合成一个动作，约 1.45 秒完成 |
| 一键校准 | 把 Y 轴开到 32000（挪出画面）→ 停 1.5 秒 → 自动识别一次 |
| 自动拼图 | 按拼好的结果，把每块碎片依次搬到位（取→转→放），再点一下停止 |
| 旋转 | 主界面上填个角度，点「旋转」就 `SET_R` 发下去，不用开设置页 |
| 状态栏 | 显示当前分辨率与**摄像头真实出帧率** |

## 界面怎么分的

主界面只留**操作时真的要按的东西**，其余全收进设置页：

```
┌ 开启摄像头 │ 设备 │ 分辨率 │        拍照保存 │ 重新扫描 │ 设置 ┐
├ 识别一次 │              点击移动 舵机 电磁铁 吸 放 一键校准 │ 连接状态 ┤
│                                                                  │
│   主画面：矫正后的板面（+ 两个浮动小窗）                          │
│                                                                  │
└ 状态栏 ────────────────────────────────────────────────────────┘
```

| 放哪 | 什么 |
| --- | --- |
| **主界面** | 开启摄像头、拍照保存、重新扫描、识别一次、点击移动、旋转、舵机、电磁铁、吸、放、一键校准、自动拼图 |
| **设置页** | 分析分辨率、显示叠加层、坐标映射（脉冲范围/板子尺寸/反向）、串口连接、PING/找零/查询/回环、手动下发、自动轮询、实时状态表、侧车日志、串口收发日志 |

设置页是盖在舞台上的整页（`#settings`），但**刻意不盖顶部工具栏**——这样「设置」按钮
一直够得着，开合时板面的尺寸也不用重算。

主界面右上角有个**连接状态**标签（`已连接 · COM3` / `未连接`）：连接按钮搬到设置页了，
不看一眼设置页也得知道连没连上。

## 串口控制台：操控 STM32 拼图机

右上角「串口控制台」按钮点开一个可折叠面板：扫串口、连接、下发 X/Y/旋转/舵机/电磁铁、
PING、触发找零（重新初始化）、周期查询实时状态，右边是收发日志。

### 舵机 / 电磁铁：工具栏上的常驻开关

这两个**不在控制台里**，在顶部工具栏上——它们是操作过程中要随手按的，不该先展开面板才能碰。
按一下立刻下发，开着的时候整颗按钮变绿，扫一眼就知道状态。

- 没连机器时两个按钮是**灰的**（点不动），提示去控制台连上。
- 按钮状态跟着**机器回报的实际状态**走，不是纯记自己点过什么——比如机器自己复位了，
  按钮会跟着变回「关」，不会一直显示开着。
- 万一命令没发出去（掉线之类），按钮会**自动翻回来**，不让它显示一个机器根本没执行的状态。

### 吸 / 放：把舵机和电磁铁合成一个动作

工具栏上的**「吸」「放」**两个按钮，各是一串动作，不是单个指令：

| | 动作 |
| --- | --- |
| **吸** | 舵机放下 → 电磁铁吸合 → 舵机升起 |
| **放** | 舵机放下 → 电磁铁释放 → 舵机升起，**并把旋转归零** |

> 「放」最后那步把旋转一起归零（`{servo: 0, rot: 0}` 一条命令带两个字段，**不额外占时间**，
> 整个动作仍然 1.45 秒）。它放在最后而不是最前，是因为那会儿碎片已经放下、工具是空的，
> 转起来不会蹭到东西。
>
> **这一步是自动拼图能成立的前提**：每轮都从「旋转 0」开始，下一块拾取时的姿态才是确定的，
> 于是转角就简化成一句「拾起来之后转到 dRot」。

整串从按下到做完约 **1.45 秒**（要求 2 秒内）。两步之间的间隔是
`renderer/host-console.js` 里的 `ACTION_STEP_MS`（默认 700ms），舵机行程长短要调就改它。

两个地方是按实测/接线定的常量，**如果用起来不对就改这两个**：

- `SERVO_DOWN` / `SERVO_UP`：舵机哪个值是「放下」。接线不同可能正好相反，
  表现为放不下或者收不回，把这两个值对调即可。
- `CALIBRATE_Y_PULSE`：一键校准把 Y 开到的脉冲（默认 32000）。

动作进行中「吸/放/舵机/电磁铁/一键校准」都会**变灰**，免得中途插手把时序打乱。

### 自动拼图（**一次一块**）

主界面上一个按钮。**点一下搬一块**，按钮上写着现在轮到第几块（`拼第 2/4 块`），
搬完自己往前走，全部搬完显示 `已拼完 4 块`。这样方便对着日志和画面一步一步调——
自动拼图出问题时，让它一口气跑完四块反而看不出是哪一步坏的。

> 换一次识别结果（重新点「识别一次」）进度就清零——碎片已经被搬过，旧路径作废了。
> 上一次已经放好的位置，再点识别时是「未拼」而不是「已拼」。

对每一块碎片走一遍：

```
1. 旋转归零
2. 移到碎片现在的位置      planPath.from → boardToPulses → 脉冲
3. 吸                     舵机放下 → 电磁铁吸合 → 舵机升起
4. 旋转到 dRot             目标姿态（拾取时工具在 0°，所以直接转 dRot 就是目标姿态）
5. 移到它的目标位置         planPath.to → 脉冲
6. 放                     舵机放下 → 释放 → 舵机升起（含旋转归零）
```

目标位置**就是画面上画的那个虚线框**——`drawOverlay` 和自动拼图用的是同一个
`currentAssemblyMap()`，不是各算各的。

**两处停留，都在设置页可调**：

| 停留 | 默认 | 加在哪 | 为什么 |
| --- | --- | --- | --- |
| **到位停留** | 800 ms | 走到位之后、动舵机之前（取和放**各一次**） | 位置对上**不等于**机器停稳了——还在晃、还在收尾，马上升降舵机会蹭到碎片 |
| **搬运停留** | 1000 ms | 吸起来之后、开始搬之前 | `吸` 的最后一步只等到命令被 ACK 就返回了，而 ACK 只代表命令**收到**——舵机这时还没真正升到位，不等就转、就走等于拖着碎片蹭 |

两条都是实测反馈出来的（「从移动到吸/放之间是连续的」「吸起到放下之间时间太短」）。

**到位怎么判**：发完移动命令后轮询 `get_all`，位置对上了就往下走。但**有超时兜底**：
puzzle-host 的协议说明里写着 `posX/posY` 是「上电找零后为 0、**只增不减**」的逻辑坐标，
万一它报的不是真实位置，轮询永远对不上——第一次等超时之后就自动**退化成固定等待**，
不会每一步都白等 8 秒。

**几条保护**：
- 没连机器 / 没识别结果 / 没拼出矩形 —— 三种情况都拒绝启动，并在日志里说明缺什么
- 跑的时候按钮变成**「停止」**，点一下就停（停在**步与步之间**，不会停在半截动作里）
- 跑的时候其余动作按钮全变灰
- 每一步都写日志（第几块、去哪儿、转多少度），出问题能照着日志回放

**顺序**就按拼接结果给的（面积从大到小，也就是按钮上「第几块」的顺序）。**不做避障**——
工具怎么走会不会蹭到别的碎片，机器那边没这个信息，现在也判断不了。

#### 看坐标：画布标签 + 设置页那张表

每块碎片的**未拼**（现在在哪）和**已拼**（拼好该在哪）都会标出坐标：

- **画布上**：路径两端各一条标签，起点写 `#0 未拼 113,135mm / 1592,10920`，
  终点写 `#0 已拼 75,76mm / 1118,7976 转-90°`
- **设置页**：卡片「搬运坐标」里一张表，四块的未拼/已拼坐标和转角列在一起，数字竖着对齐

**毫米和脉冲都给**是有意的：毫米是画面上的位置，脉冲是发给机器的值。
自动拼图出问题时先看这两列——**目标脉冲对不对**，一眼就能分出是「换算错了」还是
「机器没走到」。

### 一键校准

一个按钮，三步：**Y 轴开到标定位置 → 等它走完 → 识别一次 → 再移到板子中央**。

最后那步移到中央是为了方便接着动手——校准完工具停在画面外，什么也够不着。

两个参数**都在设置页里可调**（实测反馈：经常机器还没动到就开始校准了，所以等待要能调）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| 校准位移 Y | 32000 | Y 轴开到哪儿。注意这**超出了标定范围**（Y 是 2200~25100）——有意的，32000 是让机械臂挪出画面外的**停车位**。标定范围管的是「脉冲 ↔ 板面坐标」的换算，不是机器的行程限制 |
| 等待 | 4000 ms | 等机器真走过去再抓帧 |
| 到位停留 | 800 ms | 自动拼图里「走到位之后、动舵机之前」停多久（取和放各一次） |
| 搬运停留 | 1000 ms | 自动拼图里「吸起来之后、开始搬之前」停多久 |

等待时间**宁可给长一点**：机器的 ACK 只代表命令**收到**了，不代表走到了——不等就抓帧的话，
识别到的是机器还在半路上的画面，标定就白做了。

### 为什么又开了一个 Python 进程

渲染进程碰不到串口；主进程要自己开串口就得引原生模块（`serialport` 三个平台各自要编译）。
所以和视觉那套一样，**主进程 spawn 一个 Python**（`host/bridge.py`），两边说 JSON：

```
stdin   一行一个 JSON   = 命令（open / set / ping / get_all / poll ...）
stdout  一行一个 JSON   = 事件（status / conn / log / echo）和命令回复
stderr  任意文本        = 日志
```

它自己不实现协议，而是直接用 **`puzzle_host/`**（下面那套）里的 `ProtoClient` 和 `link`。
那套代码有 76 项测试覆盖，再写一遍纯属冒险。

### `puzzle_host/` 是 vendored 进来的第三方代码

来自同一个作者的另一个项目：**https://github.com/miaoye913/stm32-puzzle-host**，
**MIT 协议**（`puzzle_host/LICENSE` 是原件，别删）。它是一个 PC 端上位机，
通过自定义二进制帧协议（`AA 55 CMD LEN DATA... XOR 0D`）经串口操控 STM32F103 拼图机。
连它的 `vendor/`（自带 pyserial 3.5）一起搬进来了，所以**不用额外装 pyserial**。

`puzzle_host/` 里的文件**保持原样**，我们的代码（`host/bridge.py`）不混进去——
以后要跟上游同步时省事。

### 不接硬件也能全流程验证

它自带一个仿真 STM32：

```bash
python puzzle_host/demo_device.py --port 5000     # 打印「仿真 STM32 已监听 tcp://127.0.0.1:5000」
```

然后在控制台面板的串口框里手填 `tcp://127.0.0.1:5000`（那个框是可输入的下拉，不是纯选择框），
点连接——整条链路（界面 → IPC → 桥接 → 帧协议 → 设备）就跑通了，不需要任何硬件。

也可以直接跑它自己的测试：`cd puzzle_host && python -m unittest discover -s tests -t .`（76 项）。

### 一个容易误会的点

设备回的 **ACK 只代表「命令排队了」，不代表动作做完**。所以面板上的实时状态是靠周期
GET ALL 刷出来的（「自动轮询状态」那个勾），`docs` 里也写明了这点。别拿 ACK 当完成。

### 坐标映射：机器脉冲 ↔ 板面毫米

机器的 `posX/posY` 是脉冲，画面里的一切是板面像素，两者本来毫无关系。控制台面板里的
**「坐标映射」** 那一组把它们接起来，分**两级**：

```
脉冲  ──(脉冲范围 → 板子实际尺寸)──►  毫米  ──(毫米 → 板面像素)──►  画面
```

**中间这层毫米是有意加的，不是绕远路。** 直接「脉冲 ↔ 板面像素」也能用，但像素这个量纲
绑死在摄像头分辨率上——换个「分析分辨率」，同一个脉冲对应的像素值就变了，标定等于白做。
毫米只和板子、电机有关，跟摄像头一点关系没有。所以标定的落点定在毫米上，像素只是最后
一步的显示换算。

**两个轴是交叉接的**：机器的 **X 电机走的是板子的纵向**，**Y 电机走横向**。所以面板上的
两行特意标了「X 脉冲 走纵向」「Y 脉冲 走横向」——不这么标的话，看到「X 反向」一勾准星
往竖着动会发懵。这个交叉关系写在 `renderer/calibration.js` 的 `AXES_CROSSED`，
换一台不交叉接的机器就把它改成 `false`。

默认按 **A4 横向 297 × 210 mm**（实测矫正出来的板面长宽比 1.445，A4 横向是 1.414，
对得上；板子是竖放的话把「板子」那两格改成 210 × 297 就行）。

填好之后：

- 板面上叠一层**网格，刻度是毫米**——一眼就能看出标定对不对：网格读数和尺子量出来的
  实际位置对得上，说明标定是准的。
- 机器当前位置画成**十字准星**，旁边标 `脉冲(1350, 13650) → 板面(149, 105) mm`。
  没连机器就不画准星，网格照画。
- 脉冲跑出标定范围时准星会**夹在板边**并标红提示——不夹的话它会画到画布外面去，
  什么都看不见。
- X / Y 各有**反向**开关：脉冲增大时准星往哪边走，取决于电机装的方向，得能翻。
- 改完即时生效并存进 `localStorage`，不用每次重开都重填。

**反向换算 `mmToPulses()` / `boardToPulses()` 也已经写好**（同一个映射的反函数），
点画面移动机器用的就是它。它也是「把碎片的目标点翻译成机器要走多少脉冲」缺的那一步——
路径规划已经给出目标点了，配上这个换算，自动摆放就差「怎么夹、按什么顺序、走直线还是
先抬起」这几个运动学决定了。

### 点画面移动机器

面板里勾上**「点击画面移动机器」**之后，鼠标在板面上变成十字准心，**点哪儿机器就开到哪儿**：

```
点击的画布像素 → 板面像素 → 毫米 → 脉冲 → 发给机器
```

点完会画一个目标准心，并且从机器当前位置拉一条虚线过去——机器走过去的过程中虚线会
一直缩短，走完两者重合。

**默认是关着的，这是有意的**：它会动真硬件，误点一下机器就跑了，所以得有意勾上才生效。
关掉的时候点板面什么都不会发生。

还有一点要知道：机器回的 ACK 只代表**命令收到**了，不代表走到了。所以点完之后程序会补查
一次位置（让准星别看着像没反应），想连续看着机器走过去，把「自动轮询状态」也勾上。

> 标定是**两段线性**的，前提是电机行程和画面范围确实线性对应。填完建议实测对一下：
> 手动把机器走到几个位置，看准星落点对不对。要是中间对得上、两头差得多，说明有非线性
> （皮带松弛、回程差之类），两段就不够用了，得改成多点分段标定。

## OpenCV 视觉分析

### 架构：stdio 侧车，不是本地端口

Electron 主进程 `spawn` 一个 Python 进程，帧从 stdin 进、结果从 stdout 出：

```
每帧：  4 字节小端长度 + JPEG 字节   →  Python stdin
每帧：  一行 JSON                     ←  Python stdout
日志：  任意多行文本                   ←  Python stderr
```

**stdout 只走协议**，所有日志都去 stderr，否则会污染协议。用 stdio 而不是开本地端口，是因为：
不占端口、不冲突、Windows 上不弹防火墙授权框、Python 进程的生死跟着 Electron 走。

相机只被渲染进程持有，Python 从不打开设备——所以 Windows 的 DSHOW 独占、Linux 的 `video` 组权限
这些问题在侧车上都不存在。

### 算法：`vision/pipeline.py` 的 `analyze(frame)`

流程是**先矫正、再分析**：找绿板四角 → 按四角做透视矫正把板面裁出来摆正 →
在矫正后的板面上找白块和线条 → 所有坐标映射回原图返回。前端拿到的一直是原图坐标，
完全不用知道矫正这回事。

输入 BGR 帧，输出：

```json
{
  "frame":  {"width": 640, "height": 360},
  "board":  {"found": true, "corners": [[x,y], ...4 个],
             "rect_size": [368, 255],            // 矫正后板面的尺寸
             "homography": [9 个数],             // 原图 → 矫正图 的 3x3 矩阵
             "bow": {"max_px": 3.43, "ratio": 0.0092}},   // 板边弯曲量
  "pieces": [{"id": 0, "center": [x,y], "area": 9251,
              "rect": {"center": [x,y], "size": [w,h], "angle": 0.0},
              "polygon": [[x,y], ...], "angles": [91.8, 117.9, 60.3, 90.1]}],
  "lines":  [{"id": 0, "p1": [x,y], "p2": [x,y], "angle": 89.9, "length": 500,
              "width": 4.0, "color": {"rgb": [65,139,19], "hsv": [49,232,134]},
              "red": false}],
  "assembly": {"size": [240, 150], "aspect": 1.0, "fill": 1.0,
               "placements": [{"id": 0, "polygon": [[x,y], ...]}, ...]} | null,
  "timing_ms": 13.7
}
```

**要换成你自己的算法，只改这一个函数**，上下的协议、叠加层、坐标映射都不用动。

识别是**点一次算一次**，没有循环：实物摆好就不再动了，一直抽帧分析既白烧 CPU，
叠加层还一直在闪、反而看不清。`analyze()` 里顺带把碎片拼接也解了（见下），
所以一次调用的耗时里包含拼接的预算——`lib/vision-client.js` 的单帧超时因此放宽到 45 秒。

### 画面方向：`CAMERA_ROTATE_180`

摄像头是**倒着装的**（转了 180°），拍出来的画面和实物整个转了一圈。所以抽帧时先**转回来**，
后面 Python 算出来的板面图、碎片坐标、拼好的矩形、转角就全都落在「你眼里的方向」上。

这一个常量同时管三件事，改一处三处都跟着变（`renderer/renderer.js`）：
抽帧送进 Python 的那一帧、右下角的预览小窗、拍照保存的图。
**摄像头哪天正着装回来了，把它改成 `false` 就行。**

> **踩过的坑：「转 180°」和「左右翻转」不是一回事，差得很远。**
>
> 最早按「左右反了」处理，给它套了个 `scaleX(-1)`。但摄像头其实是转了 180°，
> 在已经转过 180° 的画面上再做左右翻转，**净效果是上下镜像**；
> 而且镜像会把**手性**翻过来——算出来的旋转角**符号整个反掉**。
>
> 实测反馈正是「画面上下镜像 + 角度和机器反了」两个症状一起出现，一个左右翻转就能同时
> 造成这两个。换成真正的 `rotate(180deg)` 之后两个毛病一起好了。
>
> 判断到底是「转 180°」还是「镜像」有个干脆的办法：**拍一张四象限色块**
> （左上红、右上绿、左下蓝、右下黄）。转 180° 出来是「左上黄、右上蓝」；
> 左右翻转出来是「左上绿、右上红」——两者完全不同。这个用例在
> `cam_orient` 那个界面测试里。

### 界面：为什么主画面是矫正后的板面

摄像头画面是斜的、还带着桌面背景，直接在上面画结果，角度和比例都得靠脑子换算；板子摆正之后
一眼就能看出对不对。所以主画面直接显示 `analyze()` 矫正出来的板面图，叠加层也**改用矫正空间的
坐标**画（侧车在每个碎片上多带一个 `polygon_warp`、每条线上多带 `p1_warp`/`p2_warp`），
前端不用自己再套一遍单应矩阵。原来那套「分析坐标 → 视频像素 → 屏幕像素」的投影（还带镜像）
就整个不需要了。

板面图是随结果一起回来的（`board_image_b64`，base64 的 JPEG，约 10~60KB）。**识别是一次性的**，
一帧带这点数据完全无所谓；要是还像以前那样每帧都发，就必须改协议走二进制帧了。

中间那条线用来分左右，两个区各显示各的：

- **左「拼图区」** 画**拼好的矩形**，而且是**按和碎片一样的比例**画的（1 板面像素 = 1 板面像素），
  这样两边的块大小能直接对着比；只有放不下时才缩小。
- **右「识别区」** 画**识别到的碎片**，按实际位置画，但**伸进左半边的部分裁掉**，
  免得和拼图区里的矩形糊在一起。

**线没检测到就退回板子的水平中线**——不能因为少了一条线就整个不分区、开天窗。
分界线的挑选条件是「近竖直 + 最长」。

右下角留一个小窗显示原始摄像头画面，方便对位置和光照——**那个 `<video>` 元素必须留在文档里**，
抽帧（`captureForVision`）就是从它身上抓的。

### 裁剪矫正：为什么不直接在原图上算

斜视角拍一块方板子，板面上的东西都被透视压扁了——同一个锐角，画面左边和右边量出来
的角度不一样。所以先按四角做一次 `warpPerspective`，把板面拉成正视图，之后所有角度和
面积才是有意义的几何量。四个角由 `find_board` 用 `approxPolyDP` 在多个 epsilon 下试出来。

矫正后的目标尺寸默认取**画面里量到的平均边长**（分辨率不变，所以阈值不用跟着改）。
如果知道实物的真实长宽比，把 `BOARD_REAL_ASPECT` 填上（比如 `4/3`），斜着拍也不会被压扁。

**注意区分两件事**：透视矫正修的是「拍歪了」，修不了「镜头本身的桶形/枕形畸变」——
后者要拿棋盘格标定出内参才行，光靠一张图估不准。所以这里只**量**不猜：
`board_bow()` 沿轮廓量每条边离两端连线最远有多少像素，作为畸变的观测指标。
量弯曲不能拿全部轮廓点投影（矩形对边的点也会投进同一条边的范围，实测能虚报到 258px／边长 375px），
得沿轮廓走两个角点之间那一段弧。本机实测板边偏移 0.5%~1.1%（1280×720 下 7.9px），
四条边同向，属于掩膜边缘抗锯齿的量级，**不需要矫正**。真出现明显弯曲时这个数字会先涨起来。

### 板上的线条：不认颜色，只认「和板面不一样」

线是按「偏离板面主色」找的：先取非白块像素的中位 HSV 当板面主色，再把色相/饱和度/明度
任一超出阈值、且**细长**（长宽比、长度、线宽三条一起卡）的连通域挑出来。
这样红笔、黑记号笔、板子的拼缝都抓得到，换支笔也不用改阈值。

每条线都回传**实测颜色**（rgb + hsv）和一个 `red` 粗判，侧车不猜哪条是你画的那条。
叠加层就按实测颜色画，所以是什么颜色就显示什么颜色。

一个坑：这里**故意不做 `MORPH_OPEN`**。1~3 像素宽的细线正是要找的目标，
一次开运算就把它整个磨没了——实测一条 247px 长、2px 宽的拼缝因此完全消失。

> 实测本机画面里板子中间那条线是**深绿色的拼缝**（rgb(65,139,19)、HSV(49,232,134)），
> 不是红色。严格阈值下红色像素 0 个，放宽到「偏红」也还是 0 个。所以如果画的确实是红笔，
> 请确认那支笔在镜头视野里、且颜色够饱和。

### 锐角：别把它切成好几个角

实物的尖角在掩膜里注定是被磨圆的（抗锯齿 + 形态学),尖角一圈会出现一串拐得很浅的顶点。
用统一的 epsilon 做 `approxPolyDP` 时，这些顶点各自偏离弦的量都超标，于是被原样留下——
实测一块尖角拼图因此报出 **7 个顶点**，内角 90/163/96/151/130/142/128 度，
肉眼就是「一个锐角被切成了好几个角」。

调小 epsilon 只会更糟。所以 `simplify_polygon()` 走**先粗后精**：

1. 用较粗的 epsilon（`POLY_EPS_RATIO = 0.03`，相对周长）先把「这块大概有几条边」定下来，
   尖角在这一步会被削掉一块，可以接受；
2. 反复做**直线重拟合**：把轮廓点按「离哪条边最近」分组、每条边拟合一条直线，
   角点取两侧拟合直线的交点。被削掉的那一小块仍然分别属于两条边，两条边一延长，尖点就回来了；
3. 重拟合后若还残留近乎共线的顶点（内角 > 160°），删掉再来一轮。

安全阀拿**轮廓本身的面积**当基准，而不是拿上一轮的面积：重拟合把尖角补回来，面积本来就
会变大（实测一块三角形 1618→1962，+21%），拿「变化超过 15% 就当分组错了」去拦，
等于在最需要重拟合的块上把重拟合关掉——那个三角形最终只剩 85% 面积。
现在只在结果掉出轮廓面积的 [0.70, 1.30] 倍时才回退，拦的是顶点飞掉／多边形自交这类真退化。

还有一半藏在收尾：一个**真角点**被噪声拆成两个顶点时，两个内角往往在 110°~135° 之间——
都不够「共线」（160°），一个也删不掉，于是这个角还是被报成两个。实测 JPEG 质量 80 下，
一块拼图的左侧角被拆成相距 7px 的两个顶点（111° + 133°），而不经过 JPEG 的同一帧只有 1 个。
`_merge_insignificant_edges()` 换了个判据：不看角度，看**这条边去掉了会不会改变形状**——
把短边换成一个点（两侧边延长线的交点），看由此产生/消失的三角形面积占整块多大。
真边（比如梯形那条短平行边）一去掉面积立刻变化一大截，噪声造出来的假边去掉后几乎无变化
（这里卡 1.5%）。实测这一条把 JPEG 那帧的 5 个顶点收回了 4 个，而**不经 JPEG 的帧、
以及合成的圆角尖角，顶点数一个都没变**——它只吃真正不承载形状的边。

自测里为此专门放了一块**又小又圆角**的三角形：削掉的角是固定像素量，而 epsilon 跟周长
成正比，块越小被削掉的比例越大，所以这个 bug 只在小块上现形（`--selftest` 会卡面积比）。

### 碎片拼接：`vision/assembly.py`

把识别到的碎片摆成一个矩形。做法是**束搜索 + 打分**，不是「深度优先找到第一个解就返回」：

1. 固定面积最大的那块当基准，每步把所有「把某块没放的碎片贴到某块已放碎片某条边上」的
   摆法都生成出来。
2. 每条边对有**三种**贴法：中点对齐、起点对终点、终点对起点。**中点对齐是必需的**——
   短边贴在长边正中间这种接法，光靠端对端永远表达不出来。
3. 按「贴合误差 + 外接矩形比碎块总面积大出多少」排序，只留最好的若干条继续。
4. 走完之后对每条候选打一个综合分：填充率偏离 1 的程度、外轮廓顶点数偏离 4 的程度、
   有没有拼成散开的好几坨。**取分最高的那条**。

为什么不用「精确匹配 + 是不是矩形」这种布尔判定
------------------------------------------------
先前的实现要求两块碎片的边严格等长、拼完必须刚好是矩形，否则整条分支扔掉。真实数据里
碎片角度有几个度的误差、边有几个像素的误差，**精确闭合永远差一点点，于是正确的摆法反而
全被剪掉**，搜索只能在一堆错误摆法里挑「最不难看的」——实测最好只填满外接矩形的 85%，
而且根本出不来矩形。改成打分之后，误差不再是「一票否决」，正确摆法自然排到前面。
实测同一帧：85% → **97.7%**，外轮廓 4 个顶点（真的是个矩形了）。

**「内缩几像素」是量出来的，不是拍的**
------------------------------------------------
掩膜经过 HSV 阈值 + 形态学之后，碎片的边界整体比实物大 3 像素左右，不缩的话几块之间
怎么摆都会留缝。所以 `solve()` 把内缩量也当成待定参数一起试，用拼合结果自己选最合适的
（实测最优 3px）。这个自标定是可信的：对**干净**的合成剖分它会选 0px，不会把好数据也缩掉。

求解器本身用一个**已知答案的合成剖分**验过：自己切一个 240×150 的矩形，`--selftest`
会断言它精确还原成 240×150、填充率 1.0000、碎块编号对得上。

**速度：一次识别从 9.1 秒降到约 1.5 秒（约 6 倍），结果一字不差。**
拼接占了总耗时的 98%（视觉那一段只有 10 毫秒），所以优化全在它身上：

| 改了什么 | 效果 |
| --- | --- |
| 束宽从 250 降到 40 | **最大的一笔**。实测束宽从 2000 一路降到 **5**，搜出来的尺寸、填充率、分数**完全一样**——真正有希望的分支本来就很少，宽束纯属白算 |
| 已放置块的凸包预先算好 | 原来是每个候选摆法都把已放置那几块的凸包重算一遍，而它们和候选无关。顺带加了包围盒粗筛 |
| 不再「够好了就早退」 | 填充率随内缩量是**先升后降**的，看到 0.96 就停会停在坡上拿到次优解 |
| 宽束重搜的门槛卡到 0.90 | 窄束和宽束结果一致，宽束只是兜底，而它一开就是十几倍时间。门槛设 0.97 时，960×540 下最好只到 0.9675，**每次都白跑一遍宽束，反而更慢**——这个坑踩过 |

> 关于「拉伸系数」：早先还试过把矫正的 y 拉伸系数当未知量搜（怀疑矫正偏了 15%）。
> 那是被「精确匹配」的搜索方式逼出来的——换成打分式束搜索之后，在原始比例上直接就把
> 矩形找出来了，不再需要。现在默认只用 1.0，要扫一圈得显式传 `aspect=[...]`。
>
> 每次拼接默认最多花 25 秒（`vision/pipeline.py` 的 `ASSEMBLY_TIME_BUDGET`），超时按没拼出来处理。

> 思路参考了公开的 2026 电赛 E 题解法（NUEDC-2026-E）的**做法**（束搜索 + 连续打分 +
> 多种边对齐方式）。对方是 GPL-3.0，所以这里只借鉴算法思路、代码是自己写的，没有复制。

### 搬运路径：每块碎片从哪搬到哪

识别 + 拼好之后，会在板面上画一组**搬运路径**：每块碎片从「现在在哪」连一条线到
「拼好后该在哪」，线尾带箭头，终点画一圈虚线框表示落位姿态，旁边标着这块要转多少度
（光看一条线看不出转角，所以必须标）。

拼好的矩形摆在**左半「拼图区」**、和碎片**同比例**（1 板面像素 = 1 板面像素），
所以两边的块大小能直接对着比，位移也是真实尺度的。放不下才缩。

**转角是侧车算好给的**（`placements[].rot_deg`），取的是求解时**实际施加的那个旋转矩阵**。

> 这里踩过一个坑：原先是在前端拿「碎片第 0 条边」和「目标第 0 条边」的方向相减。
> 但侧车拼接前会把碎块统一转成同一个绕向，而识别出来的轮廓是另一个绕向——
> 两边的「第 0 条边」根本不是同一条边，算出来的角度能差上百来度，
> 实测 4 块里错了 3 块（误差 18~59 像素）。改成直接用实际施加的旋转就没有这个问题了，
> 而且和绕向无关。`--selftest` 里加了一条断言把它钉住：按 `rot_deg` 转过去必须落在目标上。

**位置和转角都是在板面坐标系里算的**（`planPaths()`），也就是说算出来的位移和转角
是可以直接交给机器去执行的——现在唯一缺的就是那套「板面像素 ↔ 机器脉冲」的标定
（见上文串口控制台那节）。

> **现在只画线，不做任何运动。** 路径本身也没有做避障、没有排序（谁先搬谁后搬），
> 只是一对一的直连。真要驱动机器，还得再定：怎么夹、按什么顺序、走直线还是先抬再平移。

### 独立调试（不依赖 Electron，也不用开相机）

```bash
python vision/main.py --selftest                               # 合成图自测，验证算法本身没被改坏
python vision/main.py --source frame.jpg --save annotated.png  # 单张图 + 两张标注图
python vision/main.py --source camera:0                        # 实时开窗看效果，按 q 退出
```

`--save` 会写三张：`annotated.png` 是原图叠加，`annotated_rect.png` 是**矫正后的板面**，
`annotated_assembly.png` 是**拼好的矩形**。矫正板面那张才是算法真正在上面工作的坐标系——
判断「锐角是不是又被切成好几个角」看它最直接，每个顶点都画了点，多边形边上多出一串点
就是出问题了。拼接那张拼不出来时会明确写 `no rectangle found`。实时模式同理，会开左右两个窗口。

调阈值时用这个，比每次重启 Electron 快得多。

### 分析分辨率

界面上的「分析分辨率」默认 **960 × 540**。原来是 640 × 360，换掉是因为**短边不够准**。

> 下表的耗时只算**视觉那一段**（找板 → 矫正 → 找碎片）。**点一次「识别一次」的总耗时主要是
> 拼接求解**，约 1.5 秒——那一段的优化见下文「碎片拼接」。

| 分析分辨率 | 单帧耗时 | 逐块面积占比误差 | 顶点数 | 短边拼图那块的两个角 |
| --- | --- | --- | --- | --- |
| 1280 × 720 | 33.0 ms | — | 4 / 4 / 3 / 4 | 86.1° / 115.1°（基准） |
| **960 × 540** | **18.4 ms** | **0.7%** | **4 / 4 / 3 / 4** | **84.2° / 116.4°（差 2°）** |
| 640 × 360 | 10.1 ms | 1.7% | 4 / 4 / 3 / 4 | 76.7° / 125.9°（差 10°） |
| 480 × 270 | 8.4 ms | 3.2% | 4 / 4 / 3 / 4 | 73.0°（短边直接并没了） |

关键在于**短边**：实测那块拼图的右端只有 23px（720p）／11px（360p）长，
而抗锯齿和 JPEG 造成的边界抖动是**固定的 1px 左右，与分辨率无关**。
11px 上抖 1px 就是 9% 的角度误差，23px 上同样抖 1px 只有 4%。
所以角点精度基本是被「短边有几个像素」决定的，不是被算法决定的——
640 × 360 下那块的两个角各差 10°，960 × 540 就只剩 2°。
**如果发现某个角不准，先把分析分辨率调高一档**，比调阈值有效得多。

代价是耗时翻倍（10ms → 18ms，1280×720 是 33ms）。叠加层是按**视频分辨率**画的，
所以分析分辨率越低，误差在屏幕上被放大得越多（360p 的分析画在 720p 上，误差 ×2）。

顶点数在各分辨率下一致（4/4/3/4，JPEG q80/q50 也是）：锯齿和阈值都随分辨率变，
顶点数还能稳住，说明简化器不是在跟着噪声走。
这台开发机上界面里实测二十 ms 以内／帧；树莓派慢一个量级也还有十几 fps，够用。

抽帧时会**按目标宽高比做中心裁剪**：固定按 16:9 输出，摄像头若是 4:3 直接缩放会把角度压变形。
裁剪参数一并回传，叠加层再据此把结果坐标反映射回屏幕位置。

### 阈值不是拍脑袋来的

白块那两个阈值是照着**画面里真实像素**量的：这些块实物上不是纯白，是带蓝的浅色，
实测 BGR(230,207,175) → H≈102、S≈61–63、V≈224–230，蓝通道比红高 55。
所以饱和度上限必须给到 95——卡在 60 时整批块会被当成彩色拒掉，只剩最亮的一小块残片。

两个容易被忽略的处理：

- **只在拼板内部找白块**（`board_mask` 腐蚀 2 px 当 ROI）。板外的桌面也是浅色，
  不做 ROI 会把它整片误判成白块。
- **贴在一起的块要拆开**。七巧板常常两块挨着，连通域只剩下 3 个而不是 4 个。
  做法是逐步加大腐蚀、看连通域数量，涨不动了就停（还要按面积过滤掉噪点，
  否则一个 24 px 的杂点会把 k 抬到 5，反倒让一块 8386 px 的块一个种子都分不到），
  再用 `distanceTransformWithLabels` 按最近种子做 Voronoi 分配。

### 跨平台

- **找一个能用的 Python**：Windows 上试 `python` 再试 `python3`，Linux/Pi 上反过来；
  而且要求能 `import cv2`——装了 Python 但没装 OpenCV 是常见情况，会提示装依赖的命令。
- **Windows 二进制 stdio**：Python 默认按文本模式打开管道，会做 CRLF 转换、把 `0x1a` 当 EOF，
  二进制帧必然损坏。侧车启动时用 `msvcrt.setmode` 切到二进制模式，Linux/macOS 本来就是二进制的。
- **中文日志**：Windows 中文系统上 Python 按 cp936 编码输出，管道那头按 UTF-8 解会变乱码，
  侧车启动时把 stdout/stderr 统一 `reconfigure(encoding='utf-8')`。
- **树莓派依赖**：`opencv-python` 在 PyPI 上有 `manylinux2014_aarch64` 的预编译 wheel
  （实测 5.0.0.93 可直接下载），64 位系统上 `pip install` 就行，不用编译、也不用绕 piwheels。
- **Linux/Pi 访问摄像头**：要把用户加进 `video` 组，否则打不开 `/dev/video*`：
  ```bash
  sudo usermod -aG video $USER    # 重新登录后生效
  ```
- **Linux/Pi 访问串口**（串口控制台要用）：要加进 `dialout` 组（有些发行版是 `uucp`），
  否则报 `Permission denied`：
  ```bash
  sudo usermod -aG dialout $USER  # 重新登录后生效；用 groups 确认
  ```
  端口名：USB 转串口（CH340/CP2102/FT232）是 `/dev/ttyUSB0`，CDC/ACM 类（ST-Link 等）
  是 `/dev/ttyACM0`。插拔后编号会变，**建议用 `/dev/serial/by-id/...` 这个稳定别名**
  （面板里的串口下拉会自动列出来）。另外 `ModemManager` 有时会占住串口，
  报 `Device or resource busy` 时 `sudo systemctl stop ModemManager`。
- Electron 官方有 linux-arm64 构建，Pi 4/5 的 64 位系统直接跑得起来。
  **注意：树莓派上没实测过**，上面这些都是同一套代码路径的推断。

## 实现要点

- **权限**：`setPermissionRequestHandler` / `setPermissionCheckHandler` 只放行 `media` 与 `videoCapture`，其余请求一律拒绝。
- **安全**：`contextIsolation: true` + `nodeIntegration: false`，渲染进程只能通过 preload 暴露的接口访问文件系统；CSP 限制脚本与样式只来自本地。落盘前校验 dataURL 必须是 PNG，避免把任意内容当图片写入。
- **设备名**：未授权时 `enumerateDevices()` 的 `label` 为空，所以首次授权成功后会自动重刷一次设备列表。部分环境（如 Electron）授权前甚至返回 0 个设备，属正常。
- **帧率**：用 `requestVideoFrameCallback` 统计，而不是 `requestAnimationFrame`。后者数的是屏幕刷新率——在 165Hz 屏上会恒定显示 165，跟摄像头实际出帧速度无关。
- **背压**：分析循环 `await` 完一帧才排下一帧，慢的时候自然丢帧，不会堆积。
  另设 66 ms 的最小间隔，免得把 CPU 吃满（拼板检测每秒十几帧足够）。

## 踩坑

**启动器 `scripts/start.js` 是干嘛的**

某些环境（VS Code 扩展宿主及其派生的终端）会带着 `ELECTRON_RUN_AS_NODE=1`，这会让 electron 退化成纯 Node 进程：不显示窗口，`require('electron').app` 也是 `undefined`，报错信息还相当迷惑。启动器会显式剔除该变量再拉起 electron，所以请用 `npm start` 而不是直接敲 `electron .`。

**依赖是从哪下的**

本机 DNS 解析不了 `github.com`，而 Electron 的 postinstall 默认要去 GitHub Releases 取二进制约 100MB，会直接失败。项目里的 `.npmrc` 把二进制源指到了华为云镜像：

```
electron_mirror=https://mirrors.huaweicloud.com/electron/
```

npm 会对这行报 `Unknown project config` 警告，属预期，不影响安装。

**验证叠加层位置是否画对**

叠加层坐标对不对，肉眼在低分辨率截图上看不准（画面里几个夹子的位置会和描边糊在一起）。
可靠的查法是直接数像素：叠加层的拼板描边是精确的 `#ff8a00`，找出所有该颜色的像素，
看它们的 y 值是不是只落在拼板上边缘和下边缘两条带里。

## 常见问题

- **提示权限被拒绝**：Windows 设置 → 隐私和安全性 → 相机，打开「让桌面应用访问你的相机」。
- **提示设备不能启动（`NotReadableError`）**：多半是设备被别的程序占用，或默认摄像头指向了虚拟设备（OBS Virtual Camera、手机作摄像头之类）而其来源程序没在跑。换一个设备试试。
- **黑屏但状态正常**：有些虚拟摄像头需要先打开其来源程序。
- **勾了「OpenCV 分析」但状态栏提示找不到 Python**：按提示装依赖 `python -m pip install -r vision/requirements.txt`。
  侧车日志会记下每个候选解释器失败的原因，展开界面左下角「侧车日志」能看到。
- **拼板找不到 / 白块漏检**：先确认绿板和白块都在画面里且没被遮挡，再用
  `python vision/main.py --source 现场照片.jpg --save annotated.png` 离线调阈值（见上文「阈值不是拍脑袋来的」）。
- **板上的线没标出来**：看 `annotated.png` 里线画在不在。侧车只报「和板面颜色不一样」
  的细长结构，所以线本身得够长（超过板对角线 25%）、够细（矫正后宽于 12px 就当作块），
  并且颜色确实和绿板不同。用 `--source` 跑一张现场照片，`report()` 会把每条线的
  实测 rgb 和长度打出来，对着调 `LINE_DEV_*`。
- **锐角显示成好几个角**：先看 `annotated_rect.png`，顶点是不是真的多。
  真是的话把 `POLY_EPS_RATIO` 调大一点（线条更规整），或把 `COLLINEAR_DEG` 调小（多删共线点）。
- **左边一直显示「这几块没拼出矩形」**：这是求解器真的没搜到，不是坏了——先看
  `--selftest` 里那条「合成剖分还原成 240×150」过不过（过了就说明求解器本身没问题）。
  真实碎片拼不出来多半是**测量几何不自洽**（矫正残差把碎片拉变形了），见上文
  「碎片拼接」里那段限制说明。
- **某个角歪 / 描边没贴住那块拼图**：先确认**那块拼图的这条边在画面里有几个像素**。
  短边（几十像素以内）上的角，误差是被分辨率决定的，不是算法——先把「分析分辨率」
  调高一档看（见上文「分析分辨率」）。另外拼图在实物上有一圈浅灰色阴影，
  描边跟的是白面边界、不吃阴影，所以看起来会比肉眼看到的那块「小一圈」，这是对的。
